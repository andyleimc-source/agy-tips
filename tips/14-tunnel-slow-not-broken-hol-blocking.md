# 14 · 隧道没断，但 agy 特别慢：单条 ssh 的队头阻塞 + 只测「通不通」的健康检查

tips/13 记的是隧道**断**：本地端口消失，agy 报 `connection refused`，任务当场挂掉。这篇记的是更难查的另一半——隧道**一直是通的**，`status` 全绿，健康检查全过，但 agy 就是慢，慢到一句话要等半分钟。查线路查不出任何东西，因为线路真没问题。

顺带修正 tips/13 的一个结论：那篇写「gost 弃用」，其实弃用的只是让 gost 自己去拨 SSH 那条路。gost 做纯转发是好用的，下面就是靠它解决的。

## 症状

agy 明显变慢，同时偶尔报错终止。翻日志只能看到请求耗时变长，没有任何错误。

直接量代理耗时，才看出问题（`api.ipify.org` 是个只回一行 IP 的极小响应，用它测的就是纯往返延迟，不掺带宽）：

```
$ curl -x socks5h://127.0.0.1:7899 -o /dev/null -w "%{time_total}\n" https://api.ipify.org
26.44          ← 前置口
$ curl -x socks5h://127.0.0.1:7896 ...   8.89     ← 节点 A
$ curl -x socks5h://127.0.0.1:7895 ...   超时     ← 节点 B
$ curl -x socks5h://127.0.0.1:7897 ...   1.20     ← 拿来做基线的共享代理
```

而服务器本身完全健康：`load average: 0.08`，`ping` 244ms、0% 丢包，新开一条 SSH 到同一台机器的同一个端口，测出来稳定 1.1 秒。

## 根因 1：一条 `ssh -D` 就是一个 TCP 连接，大文件会把小请求全堵死

`ssh -D` 的 SOCKS5 代理，是把所有并发流量多路复用进**同一条 TCP 连接**。这条连接上一旦有大流量，后面排队的小请求全得等——经典的队头阻塞（head-of-line blocking）。

在 gost 的转发日志里能直接看到证据（gost 会记录每条转发的字节数和耗时）：

```
"host":"play.googleapis.com:443","inputBytes":203805334,"duration":2406228611417
"host":"daily-cloudcode-pa.googleapis.com:443","inputBytes":16977798, ...
```

一条 203MB、两条 16MB。这些是 agy 传文件/拉模型响应的正常流量，但它们占着的那条隧道上，同期所有小请求的耗时全被抬到 8~20 秒。

**这一点最坑的地方是：等你去排查的时候，大流量已经跑完了，隧道测出来一切正常。** 我第一轮就是这么被骗的——量到「新开的连接快、旧连接慢」，差点得出「长连接被限速、要定期重连」的结论。真正的鉴别方法是**先确认此刻完全没有任务在跑**（进程列表 + 看日志文件大小是否还在长），再测。静默期一测，节点 A 稳定 1.0 秒，「老连接变慢」的假设当场就废了。

**改法**：上游从 1 条加到 3 条，让前置口把并发分摊出去。这不是根治（真要根治得换成多路复用友好的协议），但成本极低、立竿见影。

## 根因 2：22 端口不只是会被黑洞，平时的路径质量也更差

tips/13 记过 22 端口会被间歇性针对黑洞，当时的处理是「22 和 443 各连一条，两条腿走路」。

这次在静默期逐条量，才发现 22 那条腿平时就不行：

| 上游 | 静默期实测（4 次） |
|---|---|
| 443 | 1.01 / 1.03 / 1.02 / 1.30 秒 |
| 22 | 16.32 / 3.10 / 1.56 / 10.73 秒 |

同一台服务器、同一个时刻、零负载，差距全来自端口。所谓「两条腿走路」，实际是**一条好腿加一条瘸腿**，而故障转移是按顺序轮的，轮到瘸腿的那些请求就是慢。

**改法**：常规池全部走 443；22 降级成纯应急——只有三条上游**同时**不健康时，才判定「443 整个被黑洞了」，自动切到 22，并在 2 小时后自动切回 443 重试。既保住了 tips/13 要的双端口保险，又不让瘸腿在日常拖后腿。

## 根因 3：健康检查只测「通不通」，这两种慢一个都抓不到

原来的健康检查是「25 秒超时内能拿到响应就算健康」。上面那些 8 秒、16 秒的请求，**全部算通过**。

健康检查测的东西必须和你在乎的东西一致：在乎的是「够不够快」，就不能只测「活没活着」。改成**通且 8 秒内**才算健康（通道正常时是 1~1.5 秒，8 秒留足了余量），一条腿慢下来就会被抓到、被 kill、被重新拉起。

⚠ **但这个阈值必须是「有条件」的，否则会亲手制造 tips/13 那类事故。** 想清楚：根因 1 说的就是「有大流量时同隧道的小请求会被堵到 8~20 秒」。要是健康检查不管三七二十一按 8 秒判，那么每当 agy 在传大文件（前面日志里那条 203MB 跑了 40 分钟），承载它的节点连续三轮判失败，大约 9 分钟后就会被 kill——**把正在传输的那条连接杀掉**。这跟 tips/13 里「一次抖动就杀」是同一个错误的不同长相。

所以阈值只在**没有任何 agy 实例在跑**的时候才作数；一旦检测到有实例活着，就退回只看通不通（25 秒）。这跟排查时的原则是同一条：**带负载量出来的慢是噪音，不是故障**。

仍然保留 tips/13 的教训：**连续 3 次不健康才 kill**，单次抖动不动手——误杀制造的真空期比慢本身更伤。

## 架构最终形态

```
agy → 127.0.0.1:7899  (gost，纯 socks5→socks5 转发，常驻，端口永不消失)
         ├─ 节点 A  127.0.0.1:7896  ← ssh -D，服务器 443
         ├─ 节点 B  127.0.0.1:7895  ← ssh -D，服务器 443
         └─ 节点 C  127.0.0.1:7894  ← ssh -D，服务器 443
```

三条上游写在**同一跳**里（`-F "socks5://A,B,C"`）才是故障转移；写成三个 `-F` 是串联三跳，第一个死了整条链就废。另外要带 `retries=3`，否则某个节点刚死时，第一个请求仍然会失败一次才切走。

改完实测：三个节点各 ~1.0 秒，前置口 0.93~1.24 秒（改前最慢 26 秒）。

## 结论

- **「通」和「够快」是两件事**，健康检查测的是哪件，决定了你能发现哪类故障。只测通不通，就永远查不出「慢」。
- **量代理性能之前，先确认没有任务在跑。** 带着负载测出来的数字全是噪音，而且噪音的形状很像「连接老化」这类错误结论。
- 单条 SSH 隧道有队头阻塞，**跑大流量的场景下多开几条上游是最省事的缓解**。
- 双端口保险不等于双端口平摊——**差的那条要降级成应急，不能进日常轮询池**。

## 涉及脚本改动

`scripts/agy-tunnel`：`front` 改成三条上游；`node_conf` 全部走 443，新增 `ssh_port()` / `FALLBACK22` 应急切换与 2 小时自动回切；`check_node` 从「通不通」改成「通且 <8 秒」，且该阈值仅在无 agy 实例运行时生效。`scripts/agy-tunnel.plist.template` 说明改成 4 个常驻 job + 1 个健康检查 job。
